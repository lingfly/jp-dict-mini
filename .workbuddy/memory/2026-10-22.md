**问题**：初版流程只有"约定"（指南对话剧本里说"先给我看"），没有状态位，AI 改文件即可绕过；`check` 也查不出"未审批就开工"。

## 补充：Proposal 必要性的澄清（同日）

**用户质疑**：后端项目的 spec 编程没有 proposal，为什么这里要？

**结论**：proposal 不是 SDD 标配，是 OpenSpec 一支的做法。Kiro 用 requirements.md、Spec Kit 用 /speckit.specify 的输入承接"为什么"，均无独立文件。

**本项目保留的理由**：缺三样后端通常已有的东西——PRD/评审会（需求只有 TODO 一行）、测试与 review（边界错了要到真机才发现）、第二个人（没人问"不做行不行"）。而 AI 的默认行为是"多做"，非目标是唯一刹车。

**proposal 的真正职责**：不是"为什么做"（一句话即可），而是「非目标 + 待确认 + 决策记录」——这三样在别处没有载体。

**已落地调整**：
- 模板顶部加「可以极简」说明：有 PRD/issue 时只填 §3 非目标、§6 待确认、§7 决策记录，其余引用链接
- specs/README 新增「先说 proposal：它不是必需品」小节，含"已有载体 → 怎么写"判断表 + 15 行极简示例
- AGENTS.md 分级表下加同一原则；指南阶段 1 开头加说明
- 技术层说明：状态与审批记录锚在 proposal.md，故文件必须存在，但内容可以只有 15 行（定位为"变更封面"而非文档仓库）

## 补充：401 并发竞态（同日）

**用户提问**：多个接口同时 401 会触发多次重登吗？

**结论**：登录请求本身不会并发——`app.js` 的 `autoWechatLogin` 用 `_loginPromise` 做了单例，同时到达的 401 共用一次登录。但存在**晚到 401 的竞态**：

- 每个 401 都无条件 `clearLoginInfo()`（清 token + storage）
- `_loginPromise` 在 finally 中置空
- 时序：A 401 → 登录 P1 → 成功写入新 token → B 的 401（慢回包）到达 → 再清 token → 触发 P2
- 结果：多一次登录，且新 token 被误清，B 的重试可能无 token 又 401

**修复要点**：请求发出时记录 token 快照，401 回包时与当前 token 比对——不同则说明已被别人刷新，直接拿新 token 重试，不清理、不登录；相同才进入重登流程，且每请求最多 1 次。

**文档更新**：AC 从 11 条扩到 14 条（追加 AC-08 并发只登一次、AC-09 晚到不清新 token、AC-10 重登仍 401 则停止提示，原 timeout 保留改为 AC-11）；design 新增竞态时序图与 401 分支流程，影响面加入 `app.js`（`_doAutoLogin` 失败应抛错而非静默返回）；tasks 扩到 15 项（T06/T07/T08 三项分别处理并发、上限、timeout）。check：14 条 AC 全覆盖。

## 发现：单次轮询失败会终止整个 AI 查询（同日）
