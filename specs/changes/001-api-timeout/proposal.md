## 1. 问题（Why）

**现象**：用户点一个按钮，转圈将近一分钟，然后弹「网络错误」；有时弹两次；有时弹完 loading 还在转。

这不是某一个接口的问题，是**请求层只有一把 60 秒的尺子**。

### 代码事实（逐条可查）

| 位置 | 现状 | 后果 |
|------|------|------|
| `utils/request.js:94` | `request(..., timeout = 60000)` | 所有未显式传值的请求都是 60 秒 |
| `utils/request.js:173` | `get(url, data, needAuth)` **没有 timeout 参数** | 35 个查询接口无法单独调优 |
| `utils/request.js:201` | `formPost(...)` **没有 timeout 参数**，`wx.request` 也未传 | 2 个表单上传走微信默认值，行为不确定 |
| `utils/request.js:274` | `put(url, data, needAuth)` **没有 timeout 参数** | 12 个更新接口固定 60 秒 |
| `utils/request.js:143` | 401 重试调用 `request(url, method, data, needAuth)` | **丢掉了 timeout**，重试后变回 60 秒 |
| `utils/request.js:157-161` | `fail` 统一 `showErrorToast('网络错误')` | 超时、断网、DNS 失败三种情况同一个文案 |
| `utils/request.js:122` | 业务码非 200 时在请求层弹 toast | 页面 `catch` 再弹一次，用户看到两个提示 |
| `utils/api.js` | **86 个接口方法，仅 1 个显式设了 timeout**（`ai-dict/query` 300 秒，且该接口**无调用方**），其余 85 个走默认 60 秒 | 一个词单列表和一次 AI 查词共用同一把尺子 |
| `utils/request.js:126-150` + `app.js:68` | 每个 401 都无条件 `clearLoginInfo()`；晚到的 401 会清掉刚刷新的新 token，并触发第二次登录 | 并发场景下多一次登录，偶发"刚登录又失效" |

### 页面层现状（统计自 `pages/`）

| 指标 | 数量 | 说明 |
|------|------|------|
| `catch` | 146 | 几乎每处网络调用都有 |
| `finally` | 37 | **约 3/4 的 catch 路径没有 finally**，loading 可能关不掉 |
| `showLoading` | 41 | 与 `hideLoading` 82 次不成对，存在重复关闭与遗漏 |
| `showToast` | 215 | 与请求层提示重叠，同一次失败可能弹两次 |

### 用户的真实经历

```text
点搜索
  → 转圈（无进度、无取消）
  → 第 60 秒：请求层弹「网络错误」
  → 页面 catch 再弹「查询失败」
  → loading 是否关闭取决于该页有没有写 finally
  → 没有重试按钮，只能退出重进
```

**谁受影响**：全部用户。弱网、地铁、电梯、后排 WiFi 场景高频。

**有多疼**：每次 60 秒，且失败后无法在原地重试，通常直接流失。

## 2. 目标（What）

在超时发生时给出**准确的失败原因**（超时 / 断网 / 服务异常）、**只提示一次**、**loading 一定关闭**，并让用户能在原页面**手动重试**。

超时值统一为 **60 秒**，集中在 `request.js` 常量表管理——本次不调整时长，只解决"报错说不清、提示重复、卡住不动、没法重试"。

> 取舍说明：统一 60 秒意味着用户仍可能等满一分钟。这是有意的：先保证行为一致、可观测，等埋点积累出真实耗时分布后再决定是否分级，避免拍脑袋调短误杀慢接口。

## 3. 非目标（Out of Scope）

- **不改后端**：网关超时、线程池、慢查询都不在本次范围
- **不做离线缓存或请求队列**：断网仍按失败处理，不承诺离线可用
- **不改 AI 查词的模型与请求协议**（异步提交 + 轮询）：只统一超时提示与阶段文案
- **不重写所有页面的错误处理**：只改高频路径（搜索、词单、复习、纠错提交），其余由请求层兜底
- **不做全局请求取消 / 竞态管理**：快速切换页面导致的结果覆盖，另开需求
- **不改 401 的自动重登策略**：只修它丢 timeout 与可能重复重试的问题

## 4. 用户与场景

| 角色 | 场景 | 现在怎么做 | 期望怎么做 |
|------|------|-----------|-----------|
| 用户 | 地铁里查词 | 转 60 秒，弹「网络错误」，退出 | 8–12 秒内提示「请求超时」，页面有「重试」 |
| 用户 | 提交复习评分时断网 | 弹一次或两次错误，卡片状态不确定 | 明确提示「未提交成功」，保留评分可重试，不跳下一张 |
| 用户 | AI 查词等待 | 转 5 分钟无进度 | 有阶段提示与取消入口（保持 300 秒上限） |
| 开发 | 排查「某个接口很慢」 | 日志只有一行「网络错误」 | 日志含 url、耗时、timeout 值、是否重试 |

## 5. 成功标准

| 类型 | 标准 | 怎么观测 |
|------|------|----------|
| 功能 | 超时提示为「请求超时，请重试」 | 改小常量触发一次 |
| 功能 | 断网提示「网络不可用」，与超时文案不同 | 离线模式点一次 |
| 功能 | 5xx 提示「服务繁忙，请稍后重试」 | mock 500 |
| 体验 | 同一次失败只弹一个提示 | 人工点一遍，数 toast |
| 体验 | 超时后 loading 一定关闭 | 逐个页面断网验证 |
| 功能 | 不自动重试任何请求 | 后端日志只收到 1 次 |
| 功能 | 三处高频页提供手动「重试」 | 点击后重新发起请求 |
| 可维护 | 超时值只在一处可改 | 改 `request.js` 常量全局生效 |
| 可观测 | 失败上报 url + 耗时 + timeout + 类型 | 微信实时日志 |

## 6. 风险与未知

| 风险 / 未知 | 影响 | 处理方式 |
|------------|------|----------|
| 统一 60 秒仍偏长 | 用户等待成本没有改善 | 本次接受；先用埋点收集耗时分布，再决定是否分级 |
| 页面太多改不完 | 行为不一致 | 请求层统一兜底，页面只改 5 个高频路径 |
| 不自动重试 | 网络抖动需要用户手动点一次 | 三个高频页提供「重试」按钮 |
| 提交即计数，切走超时会浪费 1 次额度 | 用户成本 | 结果状态保留在页面上，回来能看到发生了什么；不额外提示，避免负面情绪 |
| 老版本小程序 | 用户未更新 | 请求层改动保持向后兼容，不删旧字段 |

## 7. 决策记录

| 日期 | 决策 | 理由 | 被否决的备选 |
|------|------|------|-------------|
| 2026-10-22 | 统一 60 秒，不做分级 | 先保证行为一致，避免调短误杀慢接口 | 分级超时（8s / 12s / 20s） |
| 2026-10-22 | 超时一律不自动重试 | 避免放大后端压力、避免重复写入 | GET 自动重试一次 |
| 2026-10-22 | 超时文案固定「请求超时，请重试」 | 语义准确，直接告诉用户该做什么 | 「网络较慢，请稍后重试」 |
| 2026-10-22 | 超时值集中在常量表，页面不传具体数字 | 单点调优，避免 86 个接口各自为政 | 每个接口传 timeout |
| 2026-10-22 | AI 查词切页**不中断**轮询（方案 A） | 服务端提交即计数，中断等于白花一次；用户回来应能看到结果 | 暂停 / 取消轮询 |

## 8. 验收摘要

- AC-01 超时提示「请求超时，请重试」
- AC-02 断网提示「网络不可用」，与超时区分
- AC-03 5xx 提示「服务繁忙，请稍后重试」
- AC-04 失败后页面 loading 关闭
- AC-05 同一次失败只提示一次
- AC-06 超时不自动重试
- AC-07 失败后保留输入/卡片，并可复用已有入口重试（查询按钮、下拉刷新、「重试提交」）
- AC-08 多个请求同时 401 时只登录一次
- AC-09 晚到的 401 不清除已刷新的 token
- AC-10 重登后仍 401 则停止并提示重新打开
- AC-11 401 重试保留原 timeout
- AC-12 失败上报包含 url、耗时、timeout、类型
- AC-13 AI 查词轮询超过 5 分钟则终止并提示，期间有阶段文案
- AC-14 老页面未改造时不报错
- AC-15 重试提交时沿用首次响应时间，不把超时等待算进去
- AC-16 AI 查词切页不中断轮询，返回后展示当前状态
- AC-17 单次轮询失败不终止整个查询，连续失败 3 次或超时才终止
