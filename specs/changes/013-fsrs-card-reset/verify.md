## 六、结论

- [ ] 可以发布
- [ ] 可以发布，但需带已知问题（见 §二、§五）
- [ ] 不可发布，原因：

**发布顺序**：**后端 P0 → 后端 P1 → 前端 P2**，且 **P1 与 P2 必须同一发布窗口**。

- P0 只加列与唯一键，可独立上线（前端零改动）。
- P1 上线后前端才有接口可调。
- P2 依赖 P1 的 `epoch` 字段（`GET /api/fsrs/due` 必须已返回）。
- **AC-17 已取消**，系统不再具备"旧后端 + 新前端"的降级能力：若 P2 早于 P1 上线，入口可见但点击会 404。发布单必须签署此项（T16）。

**回滚预案**：
- P0 回滚：先 `DROP INDEX uk_traj`，再下线接口；**不要**回滚 `card_reps_before` 与 `epoch`（会影响已写入行）。备份表 `fsrs_review_log_dup` 保留，不回填。
- **`reps` 校正回滚**：从 `fsrs_card_bak_20261106` 恢复这 3 张卡的原值（7/7/9）。注意恢复后核对 SQL ①⑤ 会重新返回 3 行 / `delta=3`，属预期。
- P1 回滚：下线 `/api/fsrs/card/reset` 即可；新增的 3 列与 `fsrs_card_reset` 表保留，不影响旧逻辑。
- P2 回滚：revert 前端提交；无数据清理。**P2 回滚必须与 P1 回滚同窗口**，否则入口消失但接口残留/反之。
