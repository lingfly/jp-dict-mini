## 1. 问题（Why）

**现在发生了什么？**

### 1.1 没有任何"重新学习"入口

`utils/fsrs/index.js` 内置了 `forget(card, now, resetCount)`（第 1763 行），它能把卡片恢复为 `New`（`S=D=0`、`due=now`、`learning_steps=0`）。但全仓库**从未调用**它；`utils/api.js` 的 `fsrsApi` 只有 `due` / `due-count` / `review` / `due-forecast` / `today` 五条，没有重置接口；能力规范 `specs/capabilities/review-scheduling/spec.md` 中也没有对应 AC。

用户想"这个词我根本没学会，从头再来"时，唯一办法是继续按天复习一张 `S=46` 的卡——FSRS 会把它越排越远，实际效果是"越不会的词越少出现"。

### 1.2 复习日志没有可信的"轨迹序号"，无法切分学习轮次

`fsrs_review_log` 现有字段能定位"谁、哪个词、什么时候、评了什么"，但没有"这是第几轮学习"和"这是本轮第几次复习"。一旦引入重置，重置前后的日志会在训练时被拼成一条连续序列，而 `forget` 会把 `S/D` 归零——优化器重放时看到"稳定性从 46 掉到 0 再继续"，会把偏差算进遗忘公式（`w11~w14`），属于系统性污染。

### 1.3 幂等键对"重复评分"无效（机制问题，非数据问题）

`uk_user_word_reqid (user_id, word_id, client_request_id)` 依赖前端每次提交生成的随机 ID，而这个 ID 在 `submitReview()` **内部**生成：

```42:44:utils/fsrs/dataSource.js
function genClientRequestId() {
  return `${Date.now()}-${Math.random().toString(36).slice(2, 10)}`
}
```

调用点在 `:173`（`submitReview` 函数体内）——**每一次调用 `submitReview` 都是一个新 ID**。于是：

| 场景 | 用户意图 | 实际结果 |
|---|---|---|
| 请求超时，用户再点一次评分 | 同一次评分动作，重试 | 后端收到新 ID，视为全新动作，写第二条日志 |
| 同一张卡连点两次（不同时机的两次点击） | 两次评分 | 同上，无法区分 |

也就是说，`client_request_id` **只能挡住"同一请求对象的网络层重发"**，挡不住"用户重试"。这与 `uk_user_word_reqid` 存在的初衷（防止重复记账）不符。

> **2026-11-06 数据复验结论（推翻本提案原文的 4 条重复行证据）**
>
> 本提案首版（2026-10-30）记录的"2 张卡共 4 条冗余日志"在当前 `jp-dict` 库（MySQL 8.4.10）上**已不存在**：
>
> | 指标 | 2026-10-30 体检 | 2026-11-06 复验 |
> |---|---|---|
> | `fsrs_review_log` 行数 | 1374 | 11278 |
> | `fsrs_card` 行数 | 856 | 2387 |
> | 契约步骤 3 判定的重复行 | 4 | **0** |
> | `reps` 与日志数不一致的卡 | 2（`reps` 4 / 日志 3） | **3**（`reps` 比日志多 1） |
>
> 原样本 `word_id=2089680603696906240`（原 `reps=3`、日志 6 条）现在是 `reps=5`、日志 5 条，**已自洽**。
> 因此 `T01`「归档 4 条重复日志」在当前库上是一条**空操作**，必须改写（见 `tasks.md` T01）。
> **重复行数为 0 不代表幂等成立**——它只说明"这 4 行脏数据不在了"；机制缺口仍在（见 §1.4），且库规模增长 8 倍后更容易触发。

**谁受影响？** 全部复习用户（重置入口缺失）；后续使用日志训练 FSRS 参数的开发者（轨迹不可切分、重试造成的序号空洞无法自动修复）。

**有多疼？** 重置缺失是持续性的产品缺口；重试缺口是低频但不可逆的——一旦发生，该卡在同一轮次内的序号永久留洞，且重置**不清零 `reps`**（本提案明确决策），洞会跟着卡走到底。

**证据**：`utils/fsrs/dataSource.js:42,173` 的 ID 生成位置；下文 §1.4 的 3 例实测数据；`specs/capabilities/review-scheduling/spec.md` 全文无"重置/重新学习"。

### 1.4 已存在的历史缺口：3 例（本提案不负责修补，但必须登记）

2026-11-06 对当前库的全量核对（判据：`fsrs_card.reps` 与 `fsrs_review_log` 实际条数是否相等）：

| 指标 | 值 |
|---|---|
| 卡片总数 | 2387 |
| 有日志的卡片 | 1943 |
| 无日志且 `reps=0` 的卡片 | 444（正常，建卡后未复习） |
| **`reps` ≠ 日志数** | **3 张，全部是 `reps = 日志数 + 1`** |
| 方向相反（日志比 `reps` 多） | 0 张 |
| 全库账目 | `SUM(reps)=11281`，日志 `11278`，恰好差 3 |

三例明细（全部属于同一用户 `2086459012309630976`）：

| `word_id` | `reps` | 日志数 | 首个日志 `state` | 卡创建时间 | 缺口形态 |
|---|---|---|---|---|---|
| `2088840389390811136` | 7 | 6 | 1（应为 0） | 2026-08-18 12:07:37 | 首条日志缺失 |
| `2086421698481676288` | 7 | 6 | 1（应为 0） | 2026-08-18 12:07:37 | 首条日志缺失 |
| `2086434279682405678` | 9 | 8 | 0（正常） | 2026-08-23 21:06:47 | 中间缺一条 `rating=1` |

**成因判定：客户端失败重试，不是服务端丢数据。** 依据三条：

1. **服务端写入顺序排除了丢日志**。`FsrsCardService.review()` 是 `logMapper.insert()` → `cardMapper.updateById()`，且整体 `@Transactional(rollbackFor = Exception.class)`。日志插入失败会整体回滚，`reps` 不可能单独被加上。
2. **`reps` 由客户端计算并上传**。`review()` 直接 `card.setReps(cardReq.getReps())` 落库，服务端不做累加。前端 `scheduleNext()`（`utils/fsrs/fsrs.js:144`）内部 `reps += 1`，失败时卡片留在本地队列里、本地 `reps` 已是 +1，用户重点一次评分就是"基于已 +1 的快照再 +1"。
3. **缺口能反推出具体缺了哪一次**。日志 `state` 存的是"本次复习**前**"的状态：正常卡首条恒为 `state=0`（1941/1943 张），这两张首条是 `state=1`，说明在此之前还有一次把卡从 0 推到 1 的复习没留日志。第三张有 `state=3`（Relearning），而全库 500 条 `state=3` 中前一条是 `rating=1` 的有 420 条、前一条是 `rating=3` 的**仅此 1 条**——缺的那次正是一个 `rating=1`，这也解释了它 `lapses=1` 但日志里 `rating=1` 数为 0 的矛盾（全库唯一一例）。

**为什么只有这 3 例**：同批建卡（`created_at=2026-08-18 12:07:37`）的 20 张卡里，其余 18 张首条日志都是 `state=0`、`reps` 与日志数相等。触发条件苛刻（需在那个时刻连续失败重试或提交中杀掉小程序），概率低，但一旦发生就永久留洞。

**本提案的处置（2026-11-06 用户选定 ②）：校正 `reps`，其余不动。**

- `AC-03` 恢复为"序号连续且不重复"，不再保留"历史例外"这个口子——因为校正后历史数据也连续了。
- 校正动作：`fsrs_card.reps` 由 **7 / 7 / 9 改为 6 / 6 / 8**，与该卡实际日志条数一致；**不新增、不删除、不改写任何日志**（日志是训练事实来源，任何补写都是伪造）。
- 校正 SQL（精确到卡，不用条件推断，避免误伤）：

```sql
-- 校正历史缺口：reps 与日志条数对齐。执行前先备份 fsrs_card（见 design.md §2.5 步骤 1）。
-- 用显式 (user_id, word_id) 定位，不用 "reps <> 日志数" 动态匹配——
-- 那条语句在将来再次出现不一致时会误伤新数据。
UPDATE fsrs_card SET reps = 6
 WHERE user_id = 2086459012309630976 AND word_id IN (2088840389390811136, 2086421698481676288);
UPDATE fsrs_card SET reps = 8
 WHERE user_id = 2086459012309630976 AND word_id = 2086434279682405678;
```

- 校正后必须验证：`SELECT SUM(reps) FROM fsrs_card` = `SELECT COUNT(*) FROM fsrs_review_log`（当前应同为 11278，校正前是 11281）。

**已知代价（用户 2026-11-06 知悉并接受）**：

| 代价 | 具体影响 | 为什么会发生 |
|---|---|---|
| 用户界面计数各减 1 | 这三张卡"学过 N 次"从 7/7/9 变为 6/6/8 | `reps` 直接用于计数展示；学习统计（今日/历史）不读 `reps`，故统计不受影响 |
| **下次复习间隔会变** | 三张卡当前间隔分别为 128 / 109 / 44 天；因 `reps` 参与 fuzz 随机种子，校正后这三张卡的间隔会在 fuzz 区间内重新取值（±5%~15%） | `utils/fsrs/index.js:320-324` 的 `DefaultInitSeedStrategy` 用 `reps` 拼 seed；`utils/fsrs/fsrs.js:34` 显式 `enable_fuzz: true` |
| 校正不可自动回滚 | 若日后反悔，需人工把 6/6/8 改回 7/7/9 | 无审计列记录原值；如需可追溯，应在校正前把 `fsrs_card` 全表备份（`design.md` §2.5 步骤 1 已含） |

> **为什么选 ② 而不是 ①（登记例外）**：用户选择让账目彻底干净，代价是可预期的、有限的（3 张卡、各减 1、间隔在 fuzz 区间内浮动），而 ① 会让 `AC-03` 永远带着一个"历史例外的口子"，后续每次核对都要人工比对清单。这是用户的取舍，此处只记录后果。

## 6. 方案（结构草案，详细设计待批准后写入 `design.md`）

### 6.1 P0：日志轨迹与幂等

```sql
-- 日志表：轨迹序号 + 轮次
ALTER TABLE fsrs_review_log
  ADD COLUMN epoch INT NOT NULL DEFAULT 0 COMMENT '所属学习轮次',
  ADD COLUMN card_reps_before INT NOT NULL DEFAULT 0 COMMENT '复习前卡片 reps';
-- 因为 reps 保留（不清零），card_reps_before 全局单调，唯一键不需要 epoch
ALTER TABLE fsrs_review_log
  ADD UNIQUE KEY uk_traj (user_id, word_id, card_reps_before);
-- 版本默认值对齐实际写入值（当前 1374 条全为 5.4.1）
ALTER TABLE fsrs_review_log
  ALTER COLUMN fsrs_version SET DEFAULT '5.4.1';
```

前置清理（已知 4 条重复，先归档再建唯一键）：

```sql
CREATE TABLE fsrs_review_log_dup LIKE fsrs_review_log;
-- 保留每个 (user_id, word_id, card_reps_before) 的最小 id，其余移入 _dup
```

### 6.2 P1：重置结构

```sql
ALTER TABLE fsrs_card
  ADD COLUMN epoch INT NOT NULL DEFAULT 0 COMMENT '当前学习轮次',
  ADD COLUMN reset_count INT NOT NULL DEFAULT 0 COMMENT '累计重置次数',
  ADD COLUMN last_reset_at BIGINT DEFAULT NULL COMMENT '最近重置时间（Unix毫秒）';

CREATE TABLE fsrs_card_reset (
  id BIGINT NOT NULL,
  user_id BIGINT NOT NULL,
  word_id BIGINT NOT NULL,
  epoch INT NOT NULL COMMENT '重置后的轮次 = 重置前 +1',
  reset_at BIGINT NOT NULL,
  reset_source VARCHAR(16) NOT NULL DEFAULT 'user',
  prev_state TINYINT NOT NULL,
  prev_due BIGINT NOT NULL,
  prev_reps INT NOT NULL DEFAULT 0,
  prev_lapses INT NOT NULL DEFAULT 0,
  client_request_id VARCHAR(64) DEFAULT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_user_word_epoch (user_id, word_id, epoch),
  KEY idx_user_reset_at (user_id, reset_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='FSRS 卡片重置事件表';
```

重置语义（已确认）：

| 项 | 值 |
|----|----|
| `state` | `0 (New)` |
| `stability` / `difficulty` | `0 / 0` |
| `due` | **`now`**（用户明确） |
| `last_review` | 置 `NULL`（避免 New 卡带旧复习时间） |
| `learning_steps` | `0` |
| `reps` / `lapses` | **保留**（用户明确） |
| `epoch` | 旧值 + 1 |
| 撤销 | **不提供**（用户明确） |

### 6.3 P2：前端

- **入口**（2026-10-30 用户确认）：`pages/word-detail/word-detail`（查词、词单两个入口共用同一页面）与 `pages/review-list/review-list`（复习页答案阶段）的「更多」弹出菜单，各新增一项「重新学习」，位于「单词纠错」之上（菜单第一项）。
- **二次确认文案**（用户逐字确认）：标题「重新学习这个词？」，正文「学习进度将归零，此操作不可撤销。」，按钮「取消」「重新学习」。
- **成功后**：轻提示「已重置，将从头开始」；若当前在复习页，从本地队列移除该卡并刷新角标，不得停留在"今日复习完成"态。
- **不可用时**：服务端不支持重置能力时，两处菜单均不展示该项。**⚠️ 该项当前无实现依据**：前端无任何能力探测机制，后端 `/api/system/info` 的 `version` 为硬编码 `"1.0.0"`、不随功能变化。二选一方案见 `spec.md` AC-17 与「待确认问题」。

### 6.4 P0 增补：`clientRequestId` 复用（AC-19，2026-11-06 复核新增）

`submitReview()` 当前在函数体内生成 `clientRequestId`（`utils/fsrs/dataSource.js:173`），每次调用都是新值。改法：由调用方（`pages/review-list` 的 `handleScore()`）在一次评分动作开始时生成一次，失败重试沿用同一个值，作为参数传入 `submitReview()`。

这是让 `uk_user_word_reqid` 与 AC-02 真正生效的前提；也是 §1.4 那 3 例历史缺口不会再增加的保证。
