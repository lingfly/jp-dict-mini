# 规范编程落地指南

> 面向**从来没有用过规范编程**的程序员。
> 目标不是让你背一套流程，而是让你在下一个需求上，能少改三次、少熬一个夜。
>
> 调研时间：2026-10。案例与代码全部来自本仓库（微信小程序「日语词卡」）。

---

## 序：一个你已经遇到过的场景

打开这个项目的 `STATUS.md`，第一行写着：

> 📊 当前完成度：30%（3/13 页面）

但 `app.json` 里注册了 **29 个页面**，包括纠错、审核、反馈、复习预测、FSRS。

这两份"事实"差了半年。现在假设你对 AI 说：

> "帮我加一个复习提醒功能。"

AI 会先读文档（它被训练成相信文档），于是它认为"个人中心还没做、复习列表还没做"，然后**新建一套重复的页面**。你花了一小时 review，发现它做的东西一半是已有的，另一半不符合你的预期。

这不是 AI 笨。是**它拿到的地图是错的**。

规范编程解决的就是这件事：**让项目里始终有一份可信的、关于"应该怎么工作"的描述，人和 AI 都按它做事。**

## 第 1 章 什么是规范编程

### 1.1 一句话定义

> **规范编程（Spec-Driven Development，SDD）是先把"要什么、为什么、怎样算做对"写成可验证的文字，再让代码去满足它。**

关键词是**可验证**。不是写文档，是写"能被判断真假"的东西。

对比一下：

| 写法 | 能不能验收 |
|------|-----------|
| "搜索体验要流畅" | ❌ 无法判断 |
| "搜索无结果时，页面展示空态文案，不展示 AI 入口" | ✅ 点一遍就知道 |

### 1.2 它不是什么

| 常见误解 | 实际情况 |
|---------|---------|
| "就是写详细文档" | 文档可以没人看；规范必须能验收、能追溯、能驱动任务 |
| "就是瀑布模型" | 瀑布是"一次定死、半年后交付"；规范是"几分钟一轮、随时改" |
| "就是编码规范" | 编码规范管"怎么写"（缩进、命名）；规范编程管"写什么、为什么写" |
| "只适合大团队" | 一个人 + 一个 AI 时收益最大，因为没有第二个人帮你兜底 |
| "用了工具才算" | 工具只是脚手架。一张纸 + 四条规则也能做 |

**它和编码规范的关系**：编码规范是规范编程的**一个子集**（本项目写在 `specs/constitution.md` 的 C-01~C-12）。先有"做什么"，才轮得到"怎么写"。

### 1.3 为什么在 AI 时代突然重要

三个机制，每个都对应一个具体的痛点：

**① 外部记忆：对抗"会话失忆"**

AI 每次对话都是新的。你昨天跟它说"这个项目 ID 必须当字符串"，今天它照样写 `Number(id)`。
把结论写进 `constitution.md`，它每次动手前都会读到——**规范的第一个作用不是管人，是给 AI 装长期记忆**。

**② 可验收：对抗"看起来对"**

AI 最擅长的不是写错，是写"看起来对但不对"的代码。它能给你一个漂亮的加载动画，但忘了处理 401。
一条 AC（验收标准）就是一把尺子：`如果 token 失效，系统应重新登录且不重复弹错`。做完拿尺子量，不靠感觉。

**③ 可追溯：对抗"三个月后的自己"**

代码只能说明"现在怎么跑"，说不清"为什么这么跑"。
半年后你看到 `config.js` 里那段绕来绕去的环境判断，大概率会想"这是不是可以简化"——然后重犯一次审核被拒的事故。
规范的「决策记录」就是给未来的自己留的字条。

### 1.4 什么场景**不该**用

这一节比"怎么用"更重要，因为它决定了你会不会做两天就放弃。

| 场景 | 建议 | 原因 |
|------|------|------|
| 探索性原型（还不知道要什么） | 先随便写，**写完再补规范** | 此时需求本身就是未知数 |
| 一次性脚本、临时验证 | 不用 | 没有第二次维护 |
| 纯视觉调样式 | 不用（或只记一句"为什么用这个色"） | 规范约束不了审美 |
| 一行 bug 修复 | 不用（commit message 就是规范） | 流程成本 > 收益 |
| 需求每天都在推翻 | 先做 discovery，别急着写 spec | 写了也是白写 |

**一句话**：规范的重量，要匹配改动的重量。给改一个错别字写十页 spec，是把规范编程做成了官僚主义。

## 第 2 章 调研：现在有哪几种做法

2026 年主流的四种落地形态。你不需要全用，但要知道自己在哪一格。

| 形态 | 代表 | 工作流 | 适合谁 | 代价 |
|------|------|--------|--------|------|
| **A. 纯 Markdown + 常驻指令** | 本仓库方案 / 各种 `AGENTS.md` 实践 | 人写 spec → AI 读 → 实现 → 人验收 | 小团队、个人、存量项目 | 全靠自律，没有工具兜底 |
| **B. 工具链自动化** | GitHub Spec Kit | `/speckit.specify` → `plan` → `tasks` → `implement`，可接 30+ 种 AI 工具 | 想快速建立习惯的新手 | 任务粒度偏大；AI 拆任务的误差会叠加 |
| **C. IDE 内置** | AWS Kiro | `requirements.md`（EARS）→ `design.md` → `tasks.md`，每阶段人工确认 | 从零起的新项目 | 绑定 IDE；存量项目改造成本高 |
| **D. 变更提案制** | OpenSpec | `proposal.md` + `design.md` + `tasks.md` + spec delta，完成后 archive | 存量项目、多人协作 | 概念多，新手要花半天理解 |

### 2.1 四种形态的共同点（比差异更重要）

调研下来，无论用哪个工具，真正起作用的是同样的五件事：

1. **先写"什么算做对"，再写代码。**
2. **规范放在仓库里，和代码一起版本管理**（不要放 Wiki / 飞书 / 石墨——一个 sprint 就会过期）。
3. **规范是增量演进的**，不是一次写全。
4. **每条需求有编号，能追到任务、追到验证。**
5. **规范变更由人确认**。让 AI 自己改 spec，等于让考生自己改考卷。

这五条不需要任何工具。本项目的落地，就是把这五条做成一套最小可用的目录 + 模板 + 体检脚本。

### 2.2 本项目的选型结论

选 **A + D 的混合**，理由：

| 约束 | 影响 |
|------|------|
| 小程序、无构建链、无 npm | 不能引入重量级 CLI，脚本必须是零依赖 |
| 存量项目（29 个页面已存在） | 不能"从零重写 spec"，只能增量补录 |
| 单人 + AI 协作 | 流程必须极轻，否则一定放弃 |
| 中文语境 | 模板、AC 句式全部中文，降低认知负担 |
| 已有历史文档且已过期 | 需要明确"谁是事实来源"，否则 AI 会读错 |

**没有采用 Spec Kit 的原因**：它很好，但会引入 `specify` CLI 和一套固定命令；对本项目来说，"多一个要维护的工具"的成本高于收益。我们保留了它的核心阶段划分（specify → plan → tasks → implement），用 Markdown 手工实现。

**没有采用 Kiro 的原因**：README 里写着"开发工具：Kiro AI"，说明最初就是它生成的。但 Kiro 的 spec 是 IDE 内的，离开 IDE 就看不到；而且它是 requirements-first，更适合新项目。存量项目更需要"变更提案"，不是"重新定义需求"。

## 第 3 章 落地体系：四层 + 四级

### 3.1 四层结构

```text
┌─────────────────────────────────────────────┐
│ 第 1 层  宪法 constitution.md                │  极少变  │  "什么不能做"
├─────────────────────────────────────────────┤
│ 第 2 层  能力规范 capabilities/*/spec.md     │  随功能变 │  "现在是什么样"
├─────────────────────────────────────────────┤
│ 第 3 层  变更规范 changes/NNN-slug/            │  一次一变 │  "这次要改成什么样"
├─────────────────────────────────────────────┤
│ 第 4 层  归档 archive/ + INDEX.md            │  只增不改 │  "当时为什么这么改"
└─────────────────────────────────────────────┘
```

**为什么这样分？**

- 如果只有一份大文档，它会同时承担"原则、现状、计划、历史"四种职责，最后一定烂掉——本项目的 `README.md` 就是例子（它既是功能介绍，又是开发状态，还混着技术要点，结果全部过期）。
- 分层之后，每一层的变化频率不同：宪法一年改一次，能力规范一个月改一次，变更规范一周就归档。**变化频率不同的东西，不要放在同一个文件里。**

### 3.2 四级改动（决定你要写多少）

| 级别 | 判定标准 | 要写什么 | 时间 |
|------|----------|----------|------|
| **L0** | 单文件、≤20 行、不改行为 | 不写 | 0 |
| **L1** | ≤3 文件、单页面内、行为小改 | `proposal.md` 半页 | 10 分钟 |
| **L2** | 跨页面 / 动接口 / 动状态 | 四件套 | 30–60 分钟 |
| **L3** | 动数据契约 / 鉴权 / 不可逆 | 四件套 + `verify.md` + 人工评审 | 1–2 小时 |

**判定口诀**：

> 改完以后，如果别人需要重新理解"它应该怎么工作"，就不是 L0。

**三个真实例子（本仓库）**

| 改动 | 级别 | 理由 |
|------|------|------|
| 把"没有找到相关结果"改成"没有找到，换个词试试" | L0 | 单文件、不改行为 |
| 复习列表加下拉刷新 | L1 | 单页面，但新增了交互行为 |
| 接口超时治理（`changes/001-api-timeout/`） | L2 | 动全局请求层，影响 86 个接口 |
| 切换 `USE_MOCK` 为 false，改 FSRS 字段映射 | L3 | 动数据契约，错了会算错复习间隔 |

### 3.3 目录与命名

```text
specs/
├── constitution.md
├── capabilities/<能力名>/spec.md        # kebab-case，一个能力一个目录
└── changes/
    ├── INDEX.md                        # 需求台账：编号的唯一权威来源
    ├── _template/                       # 下划线开头 = 模板，不参与统计
    ├── 001-<slug>/                      # 进行中：编号 + 动作 + 对象
    └── archive/001-<slug>/              # 已归档：编号保留，日期记在台账
```

**编号规则（每个需求必须有）**

| 规则 | 说明 |
|------|------|
| 格式 | `#001`，三位递增 |
| 分配 | 取 `INDEX.md` 最大编号 +1；先登记一行，再建目录 |
| 复用 | **永不复用**。取消的需求也保留一行，状态写「已取消」 |
| 引用 | 对话、commit、文档统一用 `#001` |

**为什么必须有编号**

名字会变、会重、会有歧义（"那个搜索的改动"到底是哪个？）。编号不会。

三个月后你不会记得 slug 叫什么，但会记得"#007 那个上限的改法"。编号也是唯一能安全出现在 commit message 里的短标识。

**slug 命名**

- 用"动作 + 对象"：`ai-search-toggle`、`fix-401-loop`、`add-word-audio`
- 不要用 `new-feature`、`update`、`test` 这种没有信息量的名字
- 一个需求只做一件事。名字里出现 "and"，考虑拆开

分工：**编号负责唯一，slug 负责人话可读。** 两者都要有。

## 第 4 章 六个阶段，逐个讲

下面每个阶段都按同样的结构：**要回答什么 → 怎么做 → 产出 → 检查清单 → 常见错误**。
六个阶段之间还有一道**审批闸门**（阶段 2.5），它是整条流程里唯一"AI 必须停下来等人"的地方。

### 阶段 0：准备（只做一次，约 1 小时）

**要回答**：这个项目的红线是什么？AI 每次动手前必须知道什么？

**怎么做**

1. 写 `constitution.md`：只写"踩过坑的规则"，不要抄模板。判断标准是——**这条规则如果不存在，会出什么事故？** 说不出事故的，删掉。
2. 写 `AGENTS.md`：给 AI 的常驻指令。控制在 200 行内，写清项目事实、硬规则、命令。
3. 建 `specs/` 目录和模板。
4. 不要急着补录所有存量功能。只补"你接下来要改的那 2–3 个能力"。

**产出**：`constitution.md`、`AGENTS.md`、`specs/README.md`、模板

**检查清单**

- [ ] 每条宪法条款都能说出"违反后会发生什么"
- [ ] `AGENTS.md` 里没有"要写高质量代码"这种空话
- [ ] AI 读完 `AGENTS.md` 能回答：这个项目能不能装 npm 包？ID 能不能转数字？

**常见错误**

| 错误 | 后果 | 改法 |
|------|------|------|
| 抄一份通用的"代码规范" | 没人看，也不解决问题 | 只写本项目真踩过的坑 |
| 一次补录 29 个页面 | 三天后放弃 | 只补要改的，其余按需补 |
| 宪法写 50 条 | 记不住，等于没有 | 控制在 12 条以内 |

### 阶段 1：需求（Proposal）

> **先说清楚：proposal 不是 SDD 的标配。**
> Kiro 用 `requirements.md` 承接"为什么"，Spec Kit 用 `/speckit.specify` 的输入承接，只有 OpenSpec 把它单独成文件。
> 本项目采用独立文件，原因很具体：这里没有 PRD、没有评审会、没有测试，"为什么做 / 不做什么"没有别的地方可以承载。
> **如果你已经有 PRD 或 issue，只写「非目标 + 待确认 + 决策记录」三节，其余引用链接。**

**要回答**：为什么做？做到什么程度？**明确不做什么？**

**怎么做**

1. 先用一句话写清问题，必须包含事实（谁、什么场景、多疼）。
2. 写「非目标」，至少 2 条。写不出来就说明没想清楚。
3. 列出「待确认问题」，问出去。**不要替产品做决定。**
4. 判断级别。

**产出**：`proposal.md`（L1 可只写半页）

**检查清单**

- [ ] 问题描述里没有形容词（"不好用""很慢"）
- [ ] 非目标 ≥ 2 条
- [ ] 成功标准能被第三个人独立判断
- [ ] 待确认问题已发出，且没有自行假设

**常见错误**

| 反例 | 问题 | 正例 |
|------|------|------|
| "优化一下复习体验" | 无边无际 | "复习页在待复习数 > 100 时首屏加载超过 3 秒，需要降到 1 秒内" |
| 只写目标不写非目标 | 范围必然蔓延 | "本次不改评分算法，不改 UI 布局" |
| 把方案写进需求 | 锁死实现 | 需求写"用户能看到剩余次数"，不写"用 setData 更新" |

**本仓库示例**：`specs/changes/001-api-timeout/proposal.md` 的「非目标」列了 6 条，其中"不改后端""不做离线缓存""不做请求取消"直接挡住了 AI 的自由发挥。

### 阶段 2：规格（Spec）

**要回答**：改完之后，系统**应该**怎么表现？每条行为怎么判断真假？

**怎么做**

1. 用 EARS 句式写每条 AC，编号 `AC-01` 起。
2. 每条 AC 只写一件事。
3. 补异常路径：网络失败、空数据、未登录、重复提交。
4. 写 1–2 个 GIVEN/WHEN/THEN 场景，给非技术同学看。

**EARS 五种句式**

| 类型 | 句式 | 例子 |
|------|------|------|
| 事件驱动 | 当 <事件> 时，系统应 <行为> | 当用户提交非空关键词时，系统应展示加载态 |
| 状态驱动 | 在 <状态> 期间，系统应 <行为> | 在提交进行中，系统应禁用评分按钮 |
| 异常 | 如果 <条件>，系统应 <行为> | 如果请求超时，系统应保留上次结果并提示重试 |
| 可选特性 | 当 <配置> 开启时，系统应 <行为> | 当智能搜索关闭时，系统应不展示 AI 入口 |
| 普遍 | 系统应 <行为> | 系统应保持 wordId 为字符串 |

**产出**：`spec.md`（增量：只写新增/修改/删除）

**检查清单**

- [ ] 每条 AC 有唯一编号
- [ ] 没有一条 AC 提到函数名、字段名、组件名
- [ ] 每条 AC 都能被第三个人判断"过/不过"
- [ ] 至少覆盖一条异常路径
- [ ] 明确写了"不变的行为"

**常见错误**

| 反例 | 问题 |
|------|------|
| "系统应友好提示错误" | 无法判断什么是"友好" |
| "系统应支持开关" | 没说开关影响什么 |
| "系统应处理各种异常" | 范围无边，等于没写 |
| 一条 AC 里三个"并且" | 验收时无法定位是哪条没过 |

**技巧：AC 是"可执行的句子"**

写完一条 AC，问自己："我能用 5 步以内在手机上验证它吗？"不能，就还没写好。

**进阶：AC 写到哪一层（决定会不会返工）**

同一条需求，三种写法，三种结局：

| 层级 | 写法 | 实现时会发生什么 |
|------|------|-----------------|
| 意图层 | 失败时应提供重试 | AI 自由发挥：可能是按钮、可能是下拉、可能干脆自动重试 |
| 行为层 | 失败后用户无需重新输入即可再次发起请求 | 仍然不知道界面上会多出什么 |
| **界面层** | 评分条上方显示一行提示「提交超时，请重新选择」，用户再点评分按钮即重发 | 基本只有一种实现方式 |

**规则**：涉及界面的 AC，必须写到界面层，并在 `spec.md` 的「界面契约」表里落成五列：

| 列 | 要回答的 |
|----|---------|
| 出现位置 | 页面哪个区域、哪个元素的上/下/替换掉谁 |
| 形态 | 提示条 / 按钮 / 弹窗 / 图标 / **不新增元素** |
| 文案 | 逐字写出来 |
| 用户动作 | 点哪里，触发什么 |
| 消失条件 | 什么时候不再显示 |

**"不新增元素"也必须写**

真实案例（本仓库 #001）：

> 搜索失败时，AI 加了一条黄色提示条 + 「重试」。用户看图后说：**不需要这个，关键词还在，用户点查询框再查一次就行。**

如果 spec 当时写的是"**不新增元素**，靠 toast + 用户再点「查询」"，这次返工不会发生。

分歧往往不在"做成什么样"，而在"要不要加东西"。写死它。

**检验方法**

把「界面契约」表交给另一个人，问："你能照着画出这个界面吗？"

如果对方反问"重试按钮放哪？点了之后会怎样？"——说明表里还缺东西，别开工。

---

### 阶段 2.5：审批闸门（最容易被跳过的一步）

**要回答**：这个 spec 值得开工吗？范围和验收对了吗？

**为什么单独拿出来**：因为它是唯一一个"AI 必须停下来"的点。前面的文档 AI 可以自己写，后面的代码 AI 可以自己写，但"要不要做、做到什么程度"必须由人拍板。

**怎么做（全部在对话里完成，不跑命令）**

1. AI 写完 `proposal.md` + `spec.md` 后**停止**，不许碰代码。
2. AI 给你一份三行摘要：

   > **做什么**：搜索无结果时提供 AI 查词入口
   > **不做什么**：不改模型参数、不改次数上限、不做按词单差异化
   > **怎么验收**：关掉开关后，Network 面板没有任何 `/api/ai-dict/*` 请求

3. 你回一句话，二选一：
   - 认可 → 回「批准」
   - 有问题 → 指出哪里要改（这就是"打回"）
4. AI 收到「批准」后，才把状态改成 `approved`，在审批记录里写下你的原话，然后开始设计、拆任务、实现。
5. 你不需要编辑任何文档，也不需要执行任何命令。

**为什么把"批准"设计成一句话**

因为它必须足够轻，你才会真的做。如果确认需要开终端、敲命令、填表单，这个环节一定会在第三天被跳过。

代价是它比"命令 + 权限"弱：AI 理论上可以自己写一句"用户已批准"。防线有两条——审批记录必须引用你的原话（你可以核对），以及 `check` 会抓"draft 却已开工"。

**没说清楚的时候，AI 必须追问**

| 你说 | AI 应该 |
|------|---------|
| 「批准」 | 记录原话，开工 |
| 「嗯」「继续」 | **追问**："是批准实施，还是继续改文档？" |
| 「先做做看」 | 收敛范围："那我只做 X，其余记 TODO，可以吗？" |
| 「打回，XX 要改」 | 退回 draft，记录原因，改完再问一次 |

**产出的样子**

```markdown
| 日期 | 审批人 | 审核内容 | 结论 | 备注 |
|------|--------|----------|------|------|
| 2026-10-22 | 用户 | proposal + spec | 通过 | 原话：「批准，但默认值改成关闭」 |
```

**检查清单**

- [ ] 非目标 ≥ 2 条，没有"顺便做"的模糊地带
- [ ] 所有待确认已勾选并写了结论
- [ ] 每条 AC 都能在 5 步内验证
- [ ] 摘要里写了"不做什么"，不只有"做什么"

**常见错误**

| 错误 | 后果 |
|------|------|
| 把"嗯"当成批准 | 方向错了没人负责 |
| AI 自己写"用户已批准" | 闸门失效；发现后应退回 draft |
| 只看 proposal 不看 spec | 验收标准没定，最后扯皮 |
| 需求变了不重新问一次 | 代码和 spec 各走各的 |

**给 AI 的停机指令**（可直接贴）：

```text
proposal 和 spec 写完了就停。不要改代码，不要勾任务。
给我三行：做什么 / 不做什么 / 怎么验收。
然后问我"是否批准实施"，等我明确说"批准"再继续。
如果我只回了"嗯"或"继续"，你要追问一次。
```

> 这一阶段不产生代码，但它决定了后面所有代码值不值得写。

---

### 阶段 3：设计（Design）

**要回答**：怎么实现？会影响谁？出问题怎么退？

**怎么做**

1. 先填「影响面」表——**这是最重要的一步**。漏一个文件，就是一次线上事故。
2. 画数据流（文字箭头也行）。
3. 列接口约定，不确定的字段标 `待确认`。
4. 写降级与回滚。
5. 逐条对照宪法。

**产出**：`design.md`

**检查清单**

- [ ] 影响面表里每个文件都写了改动类型
- [ ] 新增的 `data` 字段有类型、初始值、含义
- [ ] 超时/空数据/未登录都有处理方式
- [ ] 写清了"前端先上还是后端先上"
- [ ] 宪法对照逐条勾选

**常见错误**

| 错误 | 后果 |
|------|------|
| 只写"改 home.js"，不写 wxml | 逻辑改了但界面没变，以为没生效 |
| 不写回滚 | 出问题时只能整个版本回退 |
| 不写"老版本兼容" | 用户没更新小程序，直接白屏 |
| 过度设计 | 一个开关写三套抽象层，维护成本翻倍 |

**一个实用规则**：影响面超过 5 个文件，考虑拆成两个 change。

---

### 阶段 4：任务（Tasks）

**要回答**：分几步做？每步怎么证明做对了？

**怎么做**

1. 一个任务 ≤ 半天，能独立验证、独立提交。
2. 每个任务标注覆盖哪条 AC。
3. 每个任务写清"怎么验证"（点哪里、看什么）。
4. 排依赖：有阻塞项放最前。

**产出**：`tasks.md`

**检查清单**

- [ ] 每条 AC 至少被一个任务覆盖（脚本会查）
- [ ] 没有"完成任务 1-5"这种打包任务
- [ ] 每个任务都有验证方式
- [ ] 阻塞项（如需后端确认）排在第一个

**好坏对比**

| 坏任务 | 问题 | 好任务 |
|--------|------|--------|
| "实现智能搜索功能" | 无法独立验证 | "首页读取配置并按开关控制入口，覆盖 AC-01/02/03，验证：关闭后无 ai-dict 请求" |
| "改一下设置页" | 不知道改什么 | "设置页新增开关并即时保存，覆盖 AC-04，验证：切换后返回首页立即生效" |

---

### 阶段 5：实现（Implement）

**要回答**：怎么让 AI 写出"符合规范"的代码，而不是"看起来像"的代码？

**怎么做（这一阶段最需要技巧）**

1. **一次只给 AI 一个任务**，把 `proposal` + 对应 AC + `design` 的影响面一起给它。
2. 明确告诉它**不要做什么**（把非目标贴进去）。
3. 让它先复述计划，再动手。
4. 做完立刻验证，通过才勾选。
5. 一个任务一次提交。

**给 AI 的指令模板**

```text
请实现 specs/changes/001-api-timeout/tasks.md 中的 T05。

上下文：
- 需求：specs/changes/001-api-timeout/spec.md 的 AC-05、AC-06
- 方案：design.md 的 §3 超时策略、§5.1 request.js 改造
- 约束：必须先读 specs/constitution.md，特别是 C-01/C-06/C-08

要求：
1. 只改 design.md 影响面表里列出的文件，不要顺手改别的
2. 不要引入任何依赖
3. 改完告诉我：改了哪些文件、每条 AC 怎么验证
4. 如果发现规范有歧义，停下来问我，不要自己决定
```

**检查清单**

- [ ] diff 只涉及影响面表里的文件
- [ ] 没有新增依赖
- [ ] 没有留下调试代码
- [ ] 每条 AC 都能手动验证

**常见错误**

| 错误 | 后果 |
|------|------|
| 一次给 AI 五个任务 | 它会把五件事揉成一坨，出问题无法定位 |
| 不说"不要做什么" | 它会热情地多改三个文件 |
| 不看 diff 直接提交 | 你可能提交了一堆 `console.log` |
| 让 AI 自己勾任务 | 它会认为"写完了"就等于"验证通过" |

---

### 阶段 6：验收与归档

**要回答**：真的做对了吗？规范更新了吗？

**怎么做**

1. 拿 `spec.md` 逐条 AC 验证，结论只有三种：通过 / 未通过 / 部分通过。
2. 补异常路径（断网、慢网、token 过期、老后端缺字段）。
3. 把 `spec.md` 的增量合并进 `capabilities/`，更新 `last_reviewed`。
4. 跑 `node scripts/spec.js check`。
5. `node scripts/spec.js archive <slug>`。

**产出**：验收记录 + 更新后的能力规范 + 归档目录

**检查清单**

- [ ] 每条 AC 都有结论和证据
- [ ] 能力规范已合并（不是"稍后补"）
- [ ] `check` 通过
- [ ] 归档后 `changes/` 里不再有它

**常见错误**

| 错误 | 后果 |
|------|------|
| "应该没问题"就算通过 | 问题留到线上 |
| 只测主流程 | 断网就白屏 |
| 归档了但没合并 spec | 规范库逐渐失真，回到起点 |
| changes 目录堆了 20 个未归档 | 没人知道哪个是当前有效的 |

**为什么必须归档**：`changes/` 是"进行中的工作台"，不是仓库。工作台堆满，就等于没有工作台。

---

### 阶段 7：维护（每月 30 分钟）

**要回答**：规范还和代码一致吗？

**怎么做**

1. 跑 `node scripts/spec.js status` 看健康度。
2. 挑一个能力规范，对照代码读一遍，改掉过期描述。
3. 看 `archive/INDEX.md`，回顾这个月改了什么、有没有反复返工的点。
4. 如果某条宪法条款连续三个月没被触发，考虑删掉（规则也会腐化）。

**漂移检测的三个信号**

| 信号 | 含义 |
|------|------|
| `check` 报"owned_paths 不存在" | 代码删了/挪了，规范没更新 |
| 同一个能力一个月改了 5 次 | 需求不稳定，或规范没写清 |
| 归档的 change 里 AC 反复"部分通过" | 验收标准写得太模糊 |

## 第 5 章 和 AI 的一次完整对话（可直接照抄）

场景：`TODO.md` 第 1 条「调用后端接口超时报错」，对应需求 **#001**。

### 第 1 轮：让它先调研，不要写代码

```text
我要做 #001：调用后端接口超时报错。

先不要改代码。请做三件事：
1. 读 utils/request.js，列出当前超时是多少、哪些方法能传 timeout
2. 统计 utils/api.js 里有多少接口、多少显式设了超时
3. 抽查 3 个页面的 catch，说明超时后用户会看到什么（提示几次、loading 关不关）

用表格给我结论，标注文件与行号。
```

**为什么这样问**：先让它把事实摆出来。直接说"帮我修超时"，它会立刻改 `request.js`。

### 第 2 轮：看它有没有找到真问题

AI 大概率会报告"默认 60 秒"。你要追问一句：

```text
再检查 401 重试分支：重试时 timeout 参数有没有传下去？
顺便统计 pages/ 里 catch 和 finally 的数量。
```

**这一步是校准**：如果它只说了"60 秒太长"，没发现 401 丢 timeout，说明调研不够深，别急着往下走。

### 第 3 轮：让它写 proposal + spec

```text
按 _template 写 proposal 和 spec，放在 specs/changes/001-api-timeout/。

要求：
- 问题部分必须有代码行号和统计数字
- 非目标至少 5 条（不改后端、不做离线队列、不做请求取消）
- AC 用 EARS，覆盖超时、断网、5xx、401、重试
- 不确定的（比如网关超时）标成「待确认」，不要猜

只写文档，不改代码。
```

### 第 3.5 轮：你回答待确认，然后说「批准」

AI 会问你三个问题（网关超时、能否重试、文案）。你回答完，它把待确认勾掉，给你摘要：

> **做什么**：分级超时 + 错误分类 + 选择性重试
> **不做什么**：不改后端、不做离线缓存、不做请求取消
> **怎么验收**：弱网下 12 秒内提示超时，只弹一次，有重试按钮
> **会改哪些文件**：`utils/request.js`、5 个页面

你回一句「批准」，它才开始写代码。

### 第 4 轮：拆任务

```text
按 _template/tasks.md 拆任务，要求：
- 请求层（T01–T07）必须连续做完再动页面
- 每个任务标注覆盖哪条 AC 和验证方式
- 阻塞项（网关超时确认）排最前
```

### 第 5 轮：一个任务一次实现

```text
实现 T05：GET 超时自动重试 1 次。

只改 utils/request.js。
要求：
- 只有 GET + TIMEOUT/SERVER 才重试
- 退避 300ms
- 最多 1 次，重试后仍失败才提示
- 不要顺手改别的分支

完成后告诉我：改了哪几行、怎么验证"后端只收到 2 次请求"。
```

### 第 6 轮：验收，不让它自评

```text
现在做验收，不要写代码：
1. 逐条列出 AC-01~AC-14，每条给出"在开发者工具里怎么点"的步骤
2. 标出你无法自行验证、需要我在真机确认的项
3. 检查 diff 有没有改到影响面之外的文件
```

### 第 7 轮：归档

```text
14 条 AC 都通过了，验收结论我填在 tasks.md 里了。

请：
1. 把 spec 的增量合并进 capabilities（补一节「全局请求约束」）
2. 更新 last_reviewed 和变更历史
3. 跑 check
4. 归档
```

**注意**：合并规范这一步，最好由人确认最终文本。可以让 AI 起草，但不能让它静默改。

## 第 6 章 让规范不腐烂的 5 个机制

规范编程失败，90% 不是"写不出来"，而是"写完就烂"。下面五个机制，按重要性排序。

### 机制 1：同批更新（写进 DoD）

**规则**：改变行为的提交，必须在同一批改动里更新规范。

**为什么有效**：规范的唯一资产是"可信"。一次不同步，后面就没人信；没人信的规范，比没有更危险——AI 会照着它自信地做错。

**怎么落到动作**：不用靠自觉，写进完成定义（`AGENTS.md` §7）：

- [ ] `specs/capabilities/` 中对应能力已更新，或明确说明"行为未变"

### 机制 2：AC 编号贯穿全链路

**规则**：`AC-01` 这个编号，要同时出现在 spec、tasks、提交信息、验收记录里。

```text
spec.md      →  AC-02 关闭时不展示 AI 入口
tasks.md     →  T02 覆盖 AC-01, AC-02
commit       →  feat(home): 按开关控制入口 [#001] (AC-02)
verify.md    →  AC-02 通过（截图）
```

**为什么有效**：任何一环断开，你都能立刻发现。比如某条 AC 没有任何任务引用，说明它被忘了；某个任务没引用任何 AC，说明它是"顺手做的"，需要警惕。

**工具兜底**：`node scripts/spec.js check` 会自动比对，报"AC-03 未被任何任务覆盖"。

### 机制 3：脚本体检（把纪律变成命令）

**规则**：每周跑一次 `check`，每次归档前必跑。

脚本只做四件事，都不需要理解业务：

| 检查 | 发现什么问题 |
|------|-------------|
| 结构完整性 | 四件套缺文件、slug 不规范 |
| AC 覆盖 | 需求写了但没人做 |
| 任务状态 | 还有未完成任务就归档 |
| owned_paths 存在性 | 代码删了/挪了，规范没跟上（漂移） |

**注意**：脚本只做"机械检查"，判断不了"这条 AC 写得对不对"。那是人的事。

### 机制 4：归档制（工作台不能堆满）

**规则**：完成的 change 必须移入 `archive/YYYY-MM-DD-<slug>/`，并在 `INDEX.md` 留一行。

**为什么有效**：

- `changes/` 里只剩"正在做的"，一眼能看出并行了几件事。
- 归档目录天然形成"决策历史"，半年后能查到"当时为什么这么改"。
- 未归档的 change 会一直躺在那里，慢慢变成"僵尸文档"。

### 机制 5：每月 30 分钟巡检

**规则**：固定一天（比如每月最后一个周五），做四件事：

1. `node scripts/spec.js status`
2. 挑一个能力规范对照代码读一遍
3. 看归档索引，找"反复返工"的模式
4. 删掉一条已经不适用的宪法条款

**为什么有效**：规范腐化是渐进的，不会自己报警。定期主动看，比出事后再补便宜得多。

### 五个反模式（看到就要停）

| 反模式 | 表现 | 后果 | 纠正 |
|--------|------|------|------|
| **让 AI 改规范** | "你顺手把 spec 更新一下" | 契约失去权威，AI 会为了自圆其说改需求 | 人确认后再落盘 |
| **过度规格化** | 一个开关写 800 行 spec | 没人读，改动成本翻倍 | 分级，L1 只写半页 |
| **规范当文档写** | 大段背景介绍、形容词 | 无法验收 | 每条都写成"当…应…" |
| **一次补全所有存量** | 给 29 个页面补 spec | 三天后放弃 | 只补要改的 |
| **只写不做** | `changes/` 堆了 10 个提案，代码没动 | 规范变成愿望清单 | 一个时间只开 1–2 个 change |

## 第 7 章 从零到熟练：30 / 60 / 90 天

不要第一天就全量上流程。下面是一条被验证过的渐进路线。

### 第 1 周：只做一件事——写 proposal

**目标**：养成"动手前先写半页"的习惯。

- 只对 L2 及以上的改动写 proposal
- 不写 spec、不写 design、不拆任务
- 每天下班前问自己：今天写的 proposal，有没有挡住一个"其实不该做"的需求？

**成功标志**：你至少有一次因为写 proposal 而发现"这个需求根本不用做"。

### 第 2–4 周：上四件套，但只在一个能力上

**目标**：跑通 2 个完整的 L2 变更。

- 选一个你最近本来就要改的功能
- 严格走 proposal → spec → design → tasks → 实现 → 归档
- 每个 change 控制在 1–2 天
- 周末花 10 分钟记录：哪一步最烦？为什么？

**成功标志**：AI 的返工次数下降；你能说出"这次它没乱改，是因为 design 的影响面写全了"。

### 第 2 个月：补录能力规范 + 引入脚本

**目标**：让规范库开始"有东西可查"。

- 补 2–3 个核心能力（不用全补）
- 每次改完代码，顺手把该能力的 spec 更新
- 开始用 `check`，每周一次

**成功标志**：新人（或新会话的 AI）能只读 `specs/` 就搞懂核心流程。

### 第 3 个月：度量与裁剪

**目标**：找到适合你的最小流程。

- 统计 4 个指标（见第 8 章）
- 删掉你觉得"写了但从不看"的部分
- 如果 L1 从来没写过 proposal，说明分级太严，放宽

**成功标志**：流程稳定在"你愿意长期做"的强度，而不是"看起来很专业"的强度。

---

## 第 8 章 怎么判断有没有用（4 个指标）

不需要工具，手工记就行。建议在 `specs/` 下建一个 `metrics.md`，每月一行。

| 指标 | 怎么算 | 看什么趋势 | 参考目标 |
|------|--------|-----------|----------|
| **返工率** | 同一功能两周内被重新打开的次数 / 总功能数 | 下降 | < 20% |
| **AI 越界次数** | AI 改了影响面之外文件的次数 / 总任务数 | 下降 | < 10% |
| **验收一次通过率** | 首轮验收全部 AC 通过的 change 数 / 总 change 数 | 上升 | > 70% |
| **规范时效** | `check` 报漂移的条数 | 下降 | 0 |

**怎么采集**（都很土，但有效）：

- 返工率：看 git log 里同一个页面的提交间隔
- 越界次数：review diff 时数一下，记在 tasks.md 的备注里
- 一次通过率：归档时看 verify 表有没有"未通过"
- 规范时效：`node scripts/spec.js status`

**一个提醒**：前两周指标一定会变差。因为你在建立规范，产出看起来慢了。**看 60 天后的趋势，不要看第一周。**

## 第 9 章 新手最常问的 15 个问题

**Q1：写规范太花时间了，一个小功能要写半小时。**

A：说明你把它写太长了。L1 只需要半页：问题、目标、非目标、验收。半小时是 L2 的成本。如果连半页都不想写，那这个改动大概率是 L0，直接做。

**Q2：需求天天变，spec 写完就废了。**

A：spec 不是合同，是当前共识的快照。需求变了就改 spec，改一行字比改一堆代码便宜。真正浪费的是"没写 spec，直接写完发现方向错了"。

**Q3：我一个人开发，写给谁看？**

A：写给三个月后的你，以及每天给你干活的 AI。单人是收益最大的场景——因为没有第二个人帮你记住"为什么这么写"。

**Q4：小程序没有单测，怎么验收？**

A：用可执行的步骤验收。AC 写成"点哪里、看什么"，验收时照着点。能在 5 步内验证的 AC 才是好 AC。本项目所有 spec 都是这个标准。

**Q5：AI 写的 spec 能直接用吗？**

A：结构可以用，判断不能。AI 擅长"补全框架"（它会把异常路径列得比你全），不擅长"做取舍"（默认值、优先级、要不要做）。**结构交给 AI，决策留给人。**

**Q6：规范要写多细？**

A：细到"第三个人能判断真假"就够，再细就是设计文档了。经验值：一个 L2 变更的 spec 控制在 100 行以内。超过 200 行，通常该拆。

**Q7：老项目怎么补？**

A：不要补全量。规则是"**要改哪个功能，就补哪个功能**"。改之前先花 20 分钟把现状写成 spec（叫"反向补录"），再按正常流程改。本项目的 3 份能力规范就是这么来的。

**Q8：团队怎么推？**

A：不要开会宣讲。找一个人、一个功能，完整跑一遍，把前后对比（返工次数、AI 乱改次数）拿出来。别人看到有效，自然会问怎么用。强推流程只会得到"形式主义"的评价。

**Q9：和 Jira / PRD 什么关系？**

A：PRD 是给人和老板看的，规范是给实现和验收看的。PRD 可以有形容词，规范不行。如果已经有 PRD，proposal 可以直接引用它，不必重写背景。

**Q10：一定要用命令吗？**

A：不用。批准、打回、验收、归档都发生在对话里：你说「批准」，AI 记录原话并改状态。`scripts/spec.js` 只是可选的体检工具，抓"未审批就开工""AC 没被覆盖""规范漂移"这类机械问题。没有 Node 也不影响流程。

**Q11：规范放在哪？Wiki 行不行？**

A：不行。必须和代码同仓库、同分支、同一次提交。放 Wiki 的规范，一个 sprint 内必然过期，因为没有人会在提交代码时顺手去改 Wiki。

**Q12：一个 change 做多久算正常？**

A：L1 半天内，L2 1–3 天。超过一周，说明要么范围太大（拆），要么需求没定（回去补 proposal）。

**Q13：AI 总是不按 spec 做，怎么办？**

A：三个检查点：① 你有没有把 spec 原文贴给它？② 有没有明确说"不要做什么"？③ 有没有让它先复述计划？三件事做了还越界，就在 `AGENTS.md` 里加一条硬规则，并把它写进宪法。

**Q14：写规范会不会限制创造力？**

A：会限制"实现方式的随意性"，不会限制"解决问题的创造力"。而且探索阶段本来就不该写规范——先随便写，找到方向后再补。

**Q15：这套东西会过时吗？**

A：工具会过时（Spec Kit、Kiro、OpenSpec 都在快速迭代），但"先把要什么说清楚"不会。本项目的目录和模板刻意做得很轻，就是为了将来换工具时，只需要换脚本，不用重写内容。

**Q16：状态由 AI 写，它自己批自己怎么办？**

A：这是这套轻量方案最弱的一环，得承认。防线有三层：

1. 审批记录必须引用你的原话——你一眼能看出自己说没说过。
2. `check` 会抓"draft 却已勾任务"，也就是"没批就开工"。
3. 发现自批，退回 `draft`，并把这条写进 `constitution.md`，要求下次明确"未获批准不得改状态"。

真要硬约束，得上 git 分支保护或 issue 状态机——单人项目通常不值得。

### 三个被反复提到的数字（供参考，非承诺）

- 单个 feature 的 spec 超过约 **800 行**，AI 的处理质量会明显下降 → 本项目把 L2 控制在 100 行内。
- 早期采用者报告 post-merge 缺陷下降 **30–50%**、首次正确实现时间缩短 **20–35%**（来源为厂商/社区调研，样本有限，仅作方向参考）。
- 规范维护的真实成本约为每个 feature **$150–400**（含评审时间），所以**分级**不是可选项，是必需项。

### 本仓库的下一步

1. **本周**：把 #001「接口超时治理」跑完（先回答 proposal 的三个待确认问题）。
2. **两周内**：给 `pages/learn` 或 `pages/word-detail` 补一份能力规范（反向补录）。
3. **一个月内**：跑一次 `node scripts/spec.js status`，根据结果裁剪模板。
4. **长期**：每月一次巡检，把过期的 `README.md` / `STATUS.md` 逐步替换为规范库入口。

### 最后一句

规范编程不让你变慢，它让你**在错误还只是一句话的时候发现错误**。

代码写错了，改的是几十行 diff；需求理解错了，改的是一整天。规范做的就是把这笔账，从"改代码"挪到"改一句话"。
