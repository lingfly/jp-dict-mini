# 规范库导览

这个目录是本项目的**事实来源**：系统现在怎么工作、下一次要改成什么样、为什么这么改，都写在这里。

代码告诉你"怎么做的"，规范告诉你"应该怎么工作、为什么"。两者不一致时，先怀疑代码，再怀疑规范，然后把它们对齐——这个过程本身就是规范编程。

---

## 一、5 分钟上手

### 场景 A：我要改一个已有功能（最常见）

```text
1. 打开 specs/capabilities/，找到对应能力的 spec.md
2. 读「行为规范」和「边界与异常」两节
3. 判断级别（见下表）。L2 以上新建需求：
   查 specs/changes/INDEX.md 最大编号 → 建 NNN-slug 目录 → 在台账登记一行
4. 让 AI 填 proposal → spec，然后【停下来】
5. AI 给你三行摘要：做什么 / 不做什么 / 怎么验收
6. 你回一句「批准」，或者指出要改的地方
7. AI 记录你的原话、把状态改成 approved，再拆 design → tasks
8. 一次做一个任务，做完勾一个
9. 全部完成后你说「验收通过」，AI 逐条核对 AC
10. 你说「归档」，AI 合并规范并移动目录（编号保留）
```

> 第 6 步是关键：**在你说「批准」之前，AI 不许写一行业务代码。**
> 整个过程你只需要说话，不需要跑任何命令。
>
> 每个需求都有编号（`#001`），以后沟通、提交、查历史都用它，不要只用名字。

### 场景 B：我只改一行文案

不用建 change，直接改。commit message 写清「改了什么/为什么」即可。

### 场景 C：我想知道"这个功能到底应该怎么表现"

只读 `specs/capabilities/`，不要读 `STATUS.md`（那是 8 月的历史快照，已经过期）。

## 二、目录地图

```
specs/
├── README.md                 ← 本文件
├── constitution.md           ← 项目宪法：12 条不可协商的规则（改代码前先看）
├── capabilities/             ← 能力规范：系统"现在"的真实行为
│   ├── word-search/          ← 查词（含 AI 查词）
│   ├── review-scheduling/    ← 复习调度（FSRS）
│   └── wordlist-group/       ← 词单分组
├── changes/                  ← 变更规范：一次改动一个目录
│   ├── INDEX.md              ← 需求台账：编号的唯一权威来源
│   ├── _template/            ← 模板（复制即用）
│   ├── 001-api-timeout/      ← 示例：#001 接口超时治理
│   └── archive/              ← 已完成，编号保留
└── guide/
    └── 规范编程落地指南.md    ← 零基础完整教程（先读这个）
```

**为什么分 capabilities 和 changes？**

- `capabilities` 回答「系统现在是什么样」——稳定、长期、按功能组织。
- `changes` 回答「这次要改成什么样」——临时、短命、按改动组织。
- 一个 change 完成后，它的结论合并进 capabilities，然后归档。这样规范不会越写越乱。

## 三、状态机：AI 在哪里必须停下来

每个 change 有一个状态，写在 `proposal.md` 的元信息表里。它不是装饰，是**闸门**。

| 状态 | 谁触发 | AI 可以做什么 | AI 不可以做什么 |
|------|--------|--------------|----------------|
| `draft` | AI 新建 change | 写 proposal / spec / design / tasks | **写业务代码、勾选任务** |
| `approved` | **用户说「批准」后，AI 写入** | 写代码、勾任务、自测 | 改需求、改 AC |
| `verified` | **用户说「验收通过」后，AI 写入** | 合并规范、归档 | 继续改代码 |
| `archived` | 用户说「归档」后，AI 移动 | 只读 | — |

### 你说什么，AI 做什么

| 你说 | AI 做什么 | 此时的要求 |
|------|-----------|-----------|
| 「批准」/「开始吧」/「按这个做」 | 状态改 `approved`，审批记录写你的原话，开始设计与实现 | 待确认清零；L2+ 已有 `spec.md` 且写了 AC |
| 「打回」/「不行」/「XX 要改」 | 退回 `draft`，记录原因，继续改文档 | — |
| 「验收通过」/「没问题」 | 逐条核对 AC，改 `verified`，合并能力规范 | 任务全完成、AC 全覆盖 |
| 「归档」 | 移入 `archive/YYYY-MM-DD-<slug>/`，更新索引 | 状态为 `verified` |

> 状态由 AI 写入，你不需要编辑文档、也不需要跑命令。
> 但**必须是你说过的原话**——AI 不能把自己的判断写成"用户已批准"。

### 「嗯」「继续」不算批准

这是最容易出问题的地方。AI 在停下来等确认时，会明确问你：

> 回复「批准」开始实施；要改就指出哪里。

如果你只回"嗯""好""继续"，规范要求 AI **追问一次**，而不是当成默认同意。

同理，"先做做看"也不是批准——它意味着范围没定，AI 应该把它收敛成 L1 的一小块，再问一次。

`check` 会检测两种越权：**draft 却已勾任务**、**verified 却还有未完成任务**。

## 四、改动分级（决定你要写多少）

| 级别 | 判定 | 要写什么 | 花多久 |
|------|------|----------|--------|
| L0 | 单文件、≤20 行、不改行为 | 不写，commit 说清 | 0 |
| L1 | ≤3 文件、单页面内 | proposal 半页 | 10 分钟 |
| L2 | 跨页面 / 动接口 / 动状态 | 四件套 | 30–60 分钟 |
| L3 | 动数据契约 / 鉴权 / 不可逆 | 四件套 + verify + 评审 | 1–2 小时 |

**核心原则：规范的重量要匹配改动的重量。** 给一行修复写十页 spec，是把规范编程做成了官僚主义，比不写还糟。

## 五、四件套各管什么

### 先说 proposal：它不是必需品

Kiro 没有独立的 proposal（`requirements.md` 承接了"为什么"），Spec Kit 也没有（`/speckit.specify` 的输入承接了）。**独立成文件是 OpenSpec 的做法**，本项目采用它，是因为这里缺三样后端项目通常已经有的东西：

| 后端项目通常有 | 这个项目 | 后果 |
|---------------|---------|------|
| PRD / 需求评审会 | 只有 `TODO.md` 一行字 | 没人定义"做到什么程度" |
| 编译期检查 + 单测 + code review | 没有测试，靠手点 | 边界错了要到真机才发现 |
| 多人协作，口头能对齐 | 一个人 + AI | 没人问"这个不做行不行" |

这三样缺失，导致"为什么做、明确不做什么"没有别的地方可以承载，只能落成文件。

**但是——如果你已经有这些载体，proposal 就该极简**：

| 你已有的 | proposal 怎么写 |
|----------|----------------|
| PRD / 需求文档 | 只填「非目标 + 待确认 + 决策记录」，背景写链接 |
| Jira / GitHub issue（含复现与验收） | 同上，issue 就是背景 |
| 一行 TODO / 口头需求 | 老老实实写全，因为它没有边界 |
| 架构改造 / 不可逆变更 | 写全，重点是决策记录 |
| 改文案 / 修 typo | 不写（L0） |

**自检**：写完 proposal，你能说出"这次明确不做什么"吗？说不出，说明它没起作用，只是一份填表练习。

> 技术上还有一层原因：状态与审批记录锚在 `proposal.md` 上，所以即使内容只有半页，文件仍然存在——它是这次变更的"封面"，不是文档仓库。

**极简 proposal 长这样**（有 Jira 时，全文 15 行）：

```markdown
# 变更：修复 401 重复登录

| 级别 | L2 | 状态 | draft |
|---|---|---|---|
| 关联 | JIRA-1234 | | |

**背景**：见 JIRA-1234，不赘述。

**非目标**
- 不改 token 刷新策略
- 不动登录页 UI

**待确认**
- [ ] **待确认** 并发请求时，是否只允许一个刷新请求在飞？

**决策记录**

| 日期 | 决策 | 理由 |
|---|---|---|
| 10-22 | 用单例 Promise 合并刷新 | 避免并发触发重复登录 |
```

没有背景章节、没有用户画像、没有成功指标——因为那些在 Jira 里已经有了。

### 四件套各管什么

| 文件 | 回答的问题 | 写不好会怎样 |
|------|-----------|-------------|
| `proposal.md` | 为什么改？改什么？**不改什么？** | 范围蔓延，做着做着跑偏 |
| `spec.md` | 改完之后，系统**应该**怎么表现？ | AI 自由发挥，验收时扯皮 |
| `design.md` | 打算怎么实现？会影响谁？ | 改一处崩三处 |
| `tasks.md` | 分几步做？每步怎么证明做对了？ | 大爆炸提交，出问题无法定位 |

四条串起来是一条可追溯链：

```
问题 → AC-01 → 任务 T02 → 代码 → 验证结论 → 能力规范更新
```

任何一环断了，三个月后没人说得清这段代码为什么长这样。

**spec 要写两层，缺一层就会返工**

| 层 | 写什么 | 缺了会怎样 |
|----|--------|-----------|
| 行为层 | AC：什么条件下系统该做什么 | 不知道算不算做完 |
| **界面层** | 「界面契约」表：位置、形态、文案、动作、消失条件 | AI 按自己的理解做，实现出来不是你要的 |

真实案例：搜索失败时 AI 加了一条黄色提示条 + 「重试」按钮，用户的答复是"不需要这个，关键词还在，点查询就行"。

原因是 spec 只写了"提供可用的重试方式"，没写「**不新增元素**」。从此这条规则进了模板。

## 六、术语速查

| 术语 | 含义 | 在本项目中的例子 |
|------|------|------------------|
| **规范（Spec）** | 对"系统应该怎么表现"的可验证描述 | "当搜索无结果时，系统应展示 AI 查词入口" |
| **能力（Capability）** | 一组相关行为的集合，规范的基本单位 | 查词、复习调度、词单分组 |
| **变更（Change）** | 一次有边界的改动，一个编号 + 一个目录 | `#001` / `001-api-timeout` |
| **增量（Delta）** | 只描述"这次增加/修改/删除了哪些行为" | `## 新增需求` 段落 |
| **AC（验收标准）** | 一条可判断真假的断言，带唯一编号 | `AC-03` |
| **EARS** | 写 AC 的句式：当…时，系统应… | 见 `_template/spec.md` |
| **漂移（Drift）** | 规范与代码不一致 | 文档说 3 个页面，实际 29 个 |
| **状态（Status）** | change 所处的审批阶段 | `draft` → `approved` → `verified` → `archived` |
| **闸门（Gate）** | 必须由人明确表态的放行点 | 你说「批准」才能写代码，说「验收通过」才能归档 |
| **归档（Archive）** | 变更完成后合并规范并移入 archive | `changes/archive/2026-10-22-xxx/` |

## 七、三个最容易踩的坑

**1. 把规范写成散文。**
"用户体验要流畅"——这句话无法验收。改成"当网络请求超过 3 秒，系统应展示 loading 骨架屏，并在 10 秒后提示重试"，才能判断做没做到。

**2. 让 AI 自己改规范。**
规范是人和 AI 之间的契约。AI 改规范等于"考生自己改考卷"。可以让 AI 提议修改，但必须由人确认后再落盘。
同理，不要让 AI 执行 `approve` / `verify`——自己批准自己，闸门就等于不存在。

**3. 写完就不管。**
规范不跟代码一起更新，一个月后就是负资产——它比没有更危险，因为大家会信它。所以本项目把"更新规范"写进了完成定义（DoD），并用 `node scripts/spec.js check` 定期体检。

## 八、没有 Node 怎么办？

流程完全不受影响：复制 `specs/changes/_template/` 到 `specs/changes/<你的slug>/`，按模板填即可。

流程本身也不依赖命令——批准、打回、验收、归档都发生在对话里。`scripts/spec.js` 只是一个可选的体检工具，主要做四件事：文件是否齐全、每条 AC 是否被任务覆盖、有没有"未批准就开工"、能力规范声明的代码路径是否还存在（漂移检测）。没有它也能工作，只是少了自动提醒。

## 九、新人第一天怎么用

1. 读 `guide/规范编程落地指南.md` 的第 1–3 章（约 15 分钟），搞懂"为什么"。
2. 读 `constitution.md`，知道哪些线不能碰。
3. 挑一个 `capabilities/` 里的 spec，对照代码读一遍，感受"规范 ↔ 代码"的对应关系。
4. 找一个 L1 的小需求，完整走一遍六阶段（约 30 分钟）。
5. 第二周再开始用 L2 四件套。**不要第一天就全量上流程。**
